## What Changed

Two independent changes ship in this batch:

**Kit 4.8 — The UAT block tells a tester who to sign in as, in both places they look.** The generated `CLAUDE.md` block that guides sessions writing UAT was 64 lines short of its source in the hub and carried one flat-wrong instruction (re-pushing a case with the same `source_ref` "updates nothing and creates nothing", where the hub actually *refreshes* it). The block is resynchronised and extended to say: name the login profile first in the module (`"Supplier — Quotes"`, `"01. Admin — Approvals"`), so the hub groups cases by who logs in; name it again as the first instruction in the steps, where a tester will read it; describe the account state needed ("a supplier user with at least one open quote", not "a user"); keep credentials out of the case entirely; and read the module back after pushing to verify the count matches, because a push timeout or wrong project looks identical to success in a transcript.

**Worklog 1.18 — Work is reported on the day it happened, not the day its session opened.** A Claude Code session keeps one id until exit, so a session opened last week and still running answers today's requests under the old session id. The report and dashboard used to select sessions for a date range by their start time, so a project worked all week showed its commits and editor time but "0 sessions" and no cost. Now each session's effort is split across the days it actually worked, weighted by burst time plus one idle cap per gap, so the days sum to exactly the session's `active_min`. Tokens are collected per day per model, so a range costs exactly what that range cost. The dashboard reloads itself every three minutes, preserving the range, project filter and scroll position. Concurrent writes to the pot are retried rather than lost, and temp files no longer match the pot's own `*.json` globs.

- For cases involving multi-day sessions, you will need to observe existing `.worklog/` data or run a test that opens a session, lets time pass (or fast-forwards the system clock), and makes commits in the second period

## Not Covered Here

- **UAT Hub push verification:** Cases UAT-4.8-11 to UAT-4.8-13 describe what the instructions say about reading back a push result; they do not execute the push itself, because `UAT_HUB_KEY` is unset on this machine. Once the key is set and a project exists, a tester can verify the push succeeds and the count returned matches.
- **Multi-day session spanning midnight:** Several worklog cases (UAT-1.18-1, UAT-1.18-2, UAT-1.18-5, UAT-1.18-6) describe work across calendar days. A tester cannot conjure such a session on demand. Observe them against existing data in `~/Worklog/slices/` by rendering historical reports, or check on the next naturally-occurring long session.
- **ActivityWatch and presence data:** The worklog report mentions elapsed vs effort. Machines without ActivityWatch or presence tracking still print the explanation paragraph; cases cover the presence of the text, not the presence of optional integrations.
- **Generated CLAUDE.md on a real repo:** Kit 4.8 cases describe the content of `CLAUDE.md` after generation. To see the real output, run `python repo_setup.py apply` or `refresh` in a test repo; do not apply changes to a production repo.
